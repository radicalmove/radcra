# Sphere LEARN and reviewer access staging design

User approved on 10 November: separate test build; actual LEARN course 3598; do not change CRJU160, its service or data, the existing Google-review demo, or the Store submission.

- Course identity is `(canonical Moodle origin, numeric course ID)` everywhere; equal numeric IDs at LEARN and UCO must not alias, move, or share comments or access. Preserve existing course UUIDs and references. Migration and testing run on disposable databases only.
- Request access is course-scoped and passwordless. New reviewer enters Name, Email address, and Requested role (Beta tester, SME, or LD/DCD). Queue one admin notice, with the request clearly marked email-unverified. An admin chooses the actual role and approves. Only then queue the browser-bound confirmation link with the assigned role and course link. Approval alone or proof alone must never issue access. Verify link in the requesting Chrome profile, then Check access on Moodle. Existing approved members on an untrusted profile receive a confirmation link without repeat admin approval. An already trusted profile reconnects with the correct email plus its stored course credential; email alone cannot grant access. Preserve reconnect, revocation and sign-out boundaries.
- Use the existing Sphere logo, blue palette and accessible, responsive form controls on request, status, confirmation and sign-in pages. Explain what happens next without exposing another user's membership state or offering global password registration as reviewer onboarding. Admin sign-in remains separate.
- Stage only: isolated service, database, extension ID/profile and captured email; no real emails, UC credentials, production records or new public endpoint. Verify automated full browser request/approve/confirm/return/reconnect and cross-origin ID collision, then exercise LEARN 3598 with a staging extension and dummy feedback only, if authenticated test access is available. Record unavailable quiz/SCORM fixtures honestly.
